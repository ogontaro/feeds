CNCF Ingress Nginx の引退で、そのまま使い続けると危うくなる構成

CNCF の Ingress Nginx が引退に向かうことで、既存の Ingress マニフェストをそのまま使い続けているクラスタがリスクを抱える、という指摘。Ingress はどのクラスタにも必ず載っている類のコンポーネントなので、引退の告知を「他人事のプロジェクト終了」ではなく自前の移行計画として読み替える必要がある。自宅クラスタでも外部公開の入口は Ingress に依存しているはずで、移行先と移行順をいつ決めるかの判断材料になる。

Kubernetes に Workload Conformance ワーキンググループが発足

クラスタの適合性を測る Certified Kubernetes や AI Conformance とは別に、ワークロードが実行時にどう振る舞うべきかを共通標準として定める WG が立ち上がった。アプリ側とクラスタ運用側の双方から意見を募っている段階なので、今のうちに関心を持っておくと、後から「標準に合っていない」と言われる前に設計を寄せられる。マルチクラスタや自前クラスタでワークロードを配る立場ほど、初期の議論を追う価値がある。

OpenTelemetry Transformation Language(OTTL)が v1 に到達

Collector Contrib v0.164.0 以降、OTTL が traces・metrics・logs のすべてで stable になり、1.x の間の後方互換が約束された。テレメトリーの加工ルールを OTTL で書いている場合、今後は構文や標準関数が壊れない前提で運用に組み込めるということ。Collector の設定を凝った形で持っているほど、アップグレード時の検証コストが下がるので、移行を先送りしていたなら判断の時期になる。

コントロールプレーンの可用性を落とす「見えにくい故障経路」

Kubernetes のコントロールプレーンは個々の故障を閉じ込めるよう設計されているが、実際の可用性はクリティカルパス上のコンポーネントの組み合わせに左右される、という整理。単一コンポーネントの冗長化だけを見ていると、障害時に想定外の連鎖が起きる余地が残る。自前でコントロールプレーンを持つ構成では、監視項目と障害訓練のシナリオをどこまで広げるかの判断材料になる。
