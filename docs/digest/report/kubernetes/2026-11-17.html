kube-proxy の IPVS バックエンド、削除スケジュールが公式ブログで示される

ipvs バックエンドは iptables より性能の高い Service 実装を目指した実験で、性能面では目的を果たしたものの、カーネルの IPVS API が Kubernetes の Services API と噛み合わず、Service のエッジケースを最後まで正しく実装できなかった、と公式が総括している。後継として 1.29 で nftables バックエンドが導入され 1.33 で GA になっており、削除までの道筋がここで明示された形だ。kube-proxy のバックエンドに ipvs を選んでいる構成は移行計画の起点になるし、kube-proxy 置き換え型の CNI を使っていても、Service 実装の選択肢が一つ消える影響は押さえておきたい。
