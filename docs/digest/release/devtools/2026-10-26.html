mise v2026.10.19

破壊的変更: セキュリティ修正の多くが「これまで通っていた操作を止める」方向なので、実質的な破壊的変更があります。lockfile_mode の既定が generate になり、mise install は毎回 mise.lock を現在の要求から作り直します（他プラットフォーム分も固定）。従来どおりに戻すには lockfile_mode = "merge" か MISE_LOCKFILE_MODE=merge を指定します。加えて、mise run --help / mise watch --help の表示、shim の実行、フックからの mise run、MCP 呼び出し、mise set / unset / tasks add の設定保存がプロジェクトの信頼と見なされなくなり、未信頼のプロジェクトでは確認が入ります。

信頼の範囲が「信頼したファイル」に紐づきました。偽装した git worktree、グローバル設定へのシンボリックリンク、.mise という名前の clone、プロジェクトの .miserc.toml が信頼を借用したりグローバル設定を隠したりできなくなり、paranoid モードでは idiomatic version file・ローカルタスクファイル・プロジェクト名の aqua レジストリが個別に信頼を要求します。commit SHA に固定したリモート git include は、その SHA を厳密にチェックアウトすることが必須になりました。タスクは、それを追加するすべての設定が信頼されている場合にだけ信頼されます。

検証は fail closed になりました。固定 checksum、Node の署名、SLSA provenance（ビルド元タグを含む）、GitHub attestation が強制され、以前のように 404 やファイル欠落で検証がスキップされることはありません。アーカイブ・アセット名・バージョン・lockfile・HTTP レスポンスは、ディレクトリ外への書き込み、無制限のメモリ・ディスク消費、プロンプトのハングを起こせなくなり、資格情報がインストールパス・lockfile・ログ・リダイレクトに出なくなります。新設定の extract_max_ratio（グローバルのみ）が展開時の膨張率を上限で抑えます。新機能では {{ mise_config_dir }}（dotfiles の variant を conf.d にリンクする用途）と mise lsp のセマンティックハイライト（initializationOptions に {"semanticTokens": false} で無効化）、github.enterprise_hosts、vfox の slsa_source_repository / slsa_source_tag が入りました。ランドスケープの「開発環境の宣言化」を mise で回している身には、lockfile がプラットフォームをまたいで mise install --locked に通るようになる変更が実利です。

同日に vfox / mise-util / mise-ui / mise-tls / mise-system / mise-system-packages / mise-sigstore / mise-settings / mise-oci の 2026.10 系タグも出ていますが、リリースノートは版号のみです。

Docker Engine (moby) v29.9.2

破壊的変更: なし。ただし eMudhra の中間 CA を使っているレジストリは、pull / push の TLS 検証が失敗するようになります。

Go ランタイムを 1.26.10 に更新し、失効した eMudhra の中間証明書 8 本を含む証明書チェーンを拒否します（CVE-2026-111943）。対象は DV / OV / EV TLS の G3B・G3C と OV コード署名の G3B・G3C で、G3B は eMudhra BV、G3C は eMudhra Inc のもの。鍵が侵害されたためで、影響を受けるレジストリは中間 CA を含まない証明書チェーンに差し替える必要があります。自前のレジストリやミラーを自宅クラスタで動かしている場合は、イメージが引けなくなって初めて気づくことになるので、アップグレード前にチェーンを確認しておくと安全です。

Devbox 0.18.5

破壊的変更: 明示的な破壊的変更はありません。ただし devbox.lock の各パッケージの plugin_version を shell / run / install が書き換えなくなり、add / rm / update のときだけ更新されるようになります（複数バージョンの devbox が混在するチームで lockfile が往復しなくなる代わりに、既存の値は次に add / rm / update するまで残ります）。

devbox.json に devbox_version（"^0.18.0" のような npm 風の制約）を書いて、プロジェクトが要求する devbox のバージョンを宣言できるようになりました。範囲外のバージョンで実行すると警告し、オブジェクト形式の {"version": "0.18.5", "on_mismatch": "error"} なら失敗します。on_mismatch: "auto" はランチャー経由でその版をダウンロードして再実行し、シェル内のネストした devbox コマンドもその版に固定します（Nix / Homebrew などランチャー無しのインストールではインストール手順付きのエラー）。DEVBOX_VERSION_POLICY=off|warn|error で CI や緊急時に上書きできます。

修正は幅広く、切れた tarball・接続リセット・curl タイムアウト・HTTP 5xx を最大 3 回リトライ、devbox run が devbox シェル内で -e / --env-file / --pure を尊重、TMPDIR に空白を含む場合のシェル、.devbox/bin/devbox シンボリックリンクがアップグレードに追随、devbox global run のフラグ受け渡し、devbox log が exit 1 しなくなる、update --all-projects が --no-install を尊重、null スクリプトでの panic、--outputs の重複、list --outdated の panic、壊れた print-dev-env キャッシュの再計算など。glibc パッチでは、パッチ済みバイナリに空の RPATH エントリが入ってローダがカレントディレクトリのライブラリを探していた問題が直っており、これはセキュリティ的にも効く修正です。devbox global を常用しているなら、devbox log の修正とグローバル run のフラグ受け渡しがそのまま効きます。
