Karpenter (aws) v1.15.0

破壊的変更: ノード修復が既定で新しい repair ディスラプションメソッドに切り替わります。従来のノード修復コントローラの挙動を維持したい場合は --legacy-node-repair（Helm では settings.legacyNodeRepair）で戻せます。また AWS 固有の feature gate が --aws-feature-gates に分離されたので、RebootForRepair など新しいゲートを使う場合は明示的な有効化が必要です。

今週の中心はノード修復の作り直しです。再起動をノードアクションとして扱えるようになり（CloudProvider.Reboot を ec2:RebootInstances で実装）、容量制約のある NodePool では置換を先に試さず terminate を先に行う terminate-first、原因（reason-aware）に応じた修復ポリシーと上限付き termination grace period、初期化に失敗したノードの修復が入りました。ノード修復は voluntary disruption として扱われ、判断の理由がメトリクスの次元に出ます。
コスト最適化とリソース要求の適正化に効く変更も多く、VPA の予測コントローラとストア、PodDeletionCostManagement（feature gate）、Pod のトポロジスプレッド既定対応、インスタンスタイプのボリューム上限を考慮したプロビジョニングが入っています。プロバイダ側では DRA の NVIDIA / EFA ドライバ対応、EC2NodeClass の Nitro Enclaves 対応、maxPodsExpression / kubeReserved / systemReserved の CEL 式対応、セキュリティグループ更新間隔の設定化、メトリクス次元の整理（disruption の判断を command と approval に分離、karpenter_pods_disrupted_total 追加）など。

aws-load-balancer-controller v3.6.0

破壊的変更: コントローラ本体の破壊的変更はありませんが、アップグレード前の CRD 再適用が要求されています（Gateway API の graduation はなく、引き続き Gateway API CRD v1.6.0 に対してビルド）。kubectl apply -k "github.com/aws/eks-charts/stable/aws-load-balancer-controller/crds?ref=master" と Gateway 用 CRD を先に適用してください。

クロスアカウントの TargetGroupBinding で、IP ターゲットを Pod の実際の Availability Zone で登録できるようになりました（opt-in。既定は従来動作なので、ゾーン単位のルーティングを効かせたいときだけ有効化します）。Ingress には frontend-nlb-status-only アノテーションが入り、ALB の手前に NLB を置く構成で status のホスト名をフロント NLB だけに絞れるため、ExternalDNS のレコード作成が直ります。Gateway API を import して使う側は、Gateway 名・finalizer・コントローラの配線をカスタマイズ可能になり、ReferenceGrant は v1 apiVersion になりました。
修正は、名前付き targetPort が複数ある Service での DuplicateTargetGroupName、ReferenceGrant のない cross-namespace TCPRoute が他名前空間の TargetGroupConfiguration finalizer を握ってしまう問題、split-horizon DNS 構成での ACM DNS 検証、セキュリティグループの CIDR 正規化、空文字の WAF ACL、informer の tombstone 処理と WatchList の full LIST フォールバックなど。
